## 記法

單位是**資訊項**（一條規則／一個主張／一個數值），**不是檔案**——檔案只是 carrier。
同一份檔案會出現在多個資訊項裡，同一個資訊項也會橫跨多個表面。

四欄：

| 欄 | 意義 |
|---|---|
| **角色** | 這項資訊在該表面上扮演什麼：現行規則／實作／操作指引／歷史紀錄／設計理由 |
| **關係** | 與另一個表面的關係：`必須同步` / `相關但解耦` / `歷史保留` |
| **同步粒度** | 若為必須同步：`字面/數值` 還是 `語意` |
| **怎麼發現漂掉** | 這次**實際**是靠什麼發現的（不是事後覺得應該怎麼發現） |

兩件依指示**先不升類**：

- **「已移除的行為仍被描述」** → 記為 **failure mode**，不另立關係類別。
- **「同義但不同寫法」** → 記為 **semantic sync 的候選性質**，不另立類別。

## § 分析：Issue #4 樣本中觀察到的共同結構（暫定）

對象：盤點表中歸類為 **semantic sync** 的 8 項——I1、I5、I6、I7、I10、I11、I12、I16。
性質：**保存觀察與候選解釋，不做設計決策。**

### A. 共同結構確實存在，但座落在「失敗的形狀」上

八項共享同一個形狀：

> 一個表面用**散文主張**某件事，另一個表面（程式或已交付的 delta）是那件事的**事實來源**；
> 不變量是兩者之間的**集合關係**。

⚠️ 共同點在**形狀**，不在**內容**。八項的內容各異（行為分類、數量、範圍清單、例外條款、
訊息片語），沒有共享詞彙能讓單一套處理涵蓋它們。

### B. 不變量多為集合關係，而非文字相等

| 項 | 不變量形狀 |
|---|---|
| I5 | proposal 列舉的 = spec delta 的 requirement 集合（**相等**） |
| I6 | 「刻意不動」∩ 實際 delta = ∅（**互斥**） |
| I10 | plan 列的閘門 ⊇ 實際阻擋的閘門（**包含**） |
| I11 | spec 記載的例外 ⊇ 程式實際的例外分支（**包含**） |
| I12 | 同 I11 |
| I7 | 散文主張的行為 ⊆ 程式實有的行為（**包含**） |
| I16 | 訊息文字 ⊇ spec Scenario 點名的片語（**包含**） |
| I1 | 對任一輸入，三個表面的判定結果相同（**相等，定義在輸入空間上**） |

八項裡 6 項是包含或互斥，只有 2 項是相等。**「同步」在這個樣本裡主要不是「對齊文字」。**

### C. source / derived 方向**不統一**

三種形狀並存：

| 方向 | 項目 |
|---|---|

### D. 可機械觀察：按「邊」分，不是按「項」分

**source 側幾乎都可機械抽取**：`git diff`、spec 的 `### Requirement:` 標題數、
函式的 early return 分支、一個字串常數。

**卡住的一律是 derived 側**——它是散文，必須先把「主張」從自然語言抽出來才能比對。

| derived 端載體 | 項數 | 有無機械檢查 |
|---|---|---|
| 散文 | 7 | **零** |
| 測試斷言（機器可讀） | 1（**I16**） | **有** |

> 八項裡唯一 derived 端可機讀的那一項，就是唯一有檢查在跑的那一項。

「難的那一半」在七項裡是**同一件事**。這既是共同結構，也正是機制做不出來的原因：
要做出來就等於要做「讀懂散文主張並與機械事實比對」——而那就是審查者在做的事。

### E. 兩個維度經檢驗**不成立為通則**，本節不升級

- **surface lifetime**：八項中只有 **I11** 有壽命錯配（例外記在會 archive 的 `design.md`，
  而 MUST 會 promote 到長期 spec），且該錯配**就是成因**。其餘七項壽命對齊。
  **1/8——特定 failure mode，不是預測因子。**
- **finding 上下游**：只有 **I5 → I6** 是真的鏈。其餘六項互相獨立。
  **1 個實例不足以稱為型態。**（初稿曾據此提出「文件面應掃相鄰而非掃同類」，
  證據不足，已收回為觀察。）

### F. 一個確實跨全部八項的性質：錯誤的散文**授權動作**
