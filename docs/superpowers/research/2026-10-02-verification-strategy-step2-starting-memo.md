## 0. 最上層的評估準則（裁定）

> Harness 的目標不是把驗證做到最多，而是**在合理的成本下，提升 AI agent 交付成果的可靠度與品質**。SDD、TDD、審查、驗證、證據、Gate 都是為這個目標服務的手段。

所以第二步評估任何驗證做法時，要問的是「它增加的保證，值不值得它的成本」，不是「它能不能增加保證」。

## 1. 成本效益由政策層決定，執行層在範圍內判斷（方向裁定，具體政策待研究）

> **方向裁定**：成本效益在策略／政策層決定。執行中的 agent **可以在政策允許的範圍內判斷實際情況，也可以往上加嚴，但不能降到政策以下**。**哪些驗證是必要的、tier 與偏離政策怎麼定義，待第二步研究後拍板**；下面的例子只是說明，還不是政策。

- **政策層（使用者）擁有**：門檻、允許的調整範圍、升級規則。例如（說明用，未拍板）：程式行為一律 TDD；必要的保證不能降級；用 tier 決定審查的基準深度。
- **執行層（agent）**：在範圍內判斷實際情況。這與現行 `auto-loop.md` 一致：它把時機、批次與深度交給 agent 判斷，並要求在需要時往上加嚴（「a baseline, not a ceiling」），從不允許降到基準以下。
- **政策沒涵蓋的情況**：升級成「偏離／降級 → 留紀錄 → 交更高層裁定」。**留紀錄本身不能追認一個原本就被禁止的完成**。正式設計已經分開「預先授權、可降級的 fallback」與「required 能力缺了就 BLOCK，或回 proposal 改契約並重新核可」；核心完整性條件不可被覆寫（正式設計 §2.1–§2.3）。
- 理由：讓正在做事的 agent 當場決定「要不要跳過」，它幾乎一定會往「先跳過」偏（Superpowers TDD skill 有一節「Common Rationalizations」，就是因為這個）。這也是守住「TDD 不可丟」這條硬約束的護欄。
- 一句話：**依成本訂政策；執行者可以加嚴、不能降級；紀錄不能追認禁止事項。**

（本節依 Codex 研究評論 2026-10-02 修正：原寫「執行時 agent 不當場重新判斷」，與現行 auto-loop 衝突。）

## 2. 兩根軸：觀察方式 vs TDD 紀律（假說）

- **觀察方式（oracle／method）由受測對象決定**：程式行為用 unit／integration test；agent 行為用執行者跑情境加評分器；結果固定的規則用 conformance／mutation；遷移用前後對帳；多表面契約用一致性檢查；上游相容用雙版本對照。
- **TDD 紀律能不能套用另外判斷**：是否存在一個**可重跑、而且在改動前就會失敗**的觀察方式。
- 佐證：Superpowers `writing-skills`（本機快取 v6.3.0）明文把 TDD 套用在寫 skill 上（沒有 skill 時派 subagent 跑壓力情境看它違反規則 → 加上 skill 後看它遵守）；Identity 用盲測執行者當觀察工具跑 RED→GREEN。
- ~~推論：§4.3 與 2026-09-07 裁定可能是在回答兩個不同的問題~~ → **Codex 研究評論反駁（2026-10-02）**：兩者都明文在管 applicability，不能據此宣稱衝突消失。比較精確的拆法是四件事：**觀察方式、做不做得到（feasibility）、有沒有義務做（policy obligation）、RED 是否有效（validity）**。「有一個會失敗、可重跑的觀察」只證明做得到，不證明有義務做，也不證明失敗原因有效（spec REQ-2）。ID brainstorm Q11 早已區分「能做 TDD」與「必須進 TDD 政策」。這個拆法可能解掉 P2 的一部分，但要先驗證，不能直接宣告衝突消失。
- 程式底線（假說）：若 change 改變或承諾維持可執行程式的行為，該行為應形成獨立的 verification subject，不能因為同一個 change 同時涉及其他 subject，就繞過既定的 TDD 要求。注意「有程式 diff」不等於「有需要新 RED/GREEN 的行為 claim」：純重構、產生出來的檔案、排版調整都會讓這兩者分開，這正是要研究的邊界。
- 分流的單位是「這個 claim 在驗什麼」，不是整個 change 的類型。先例：spec `tdd-evidence-contract` REQ-2「配對的單位是 subject，不是 task」。

## 3. 候選 Assurance 分層：不是每個 PASS 都一樣強（假說；屬產品承諾層級，最後要走正式設計修訂）

- 正式設計 §2 已經把保證收窄成「保證流程、不保證內容正確」；§8 第 2 條明列 prompt／instruction 文字層的正確性不保證；§4.2 的四種方法本來就不只服務程式；§4.2 定義「能重算」一律指程式可重算。
- 目前缺的不是「准哪些類型進來」，而是**每一類 PASS 能宣稱到哪裡**。正式設計的 Verification Result 最終都收斂成相同的 PASS／FAIL／BLOCKED（§2.1 I6）；現有 Gate 能不能分辨不同 PASS 背後的保證強弱，**待查證**。
- 候選劃線（**只是思考用的候選，不固化成三圈模型**）：
  - **較強**：觀察方式可由機器執行，**而且在明確的條件下可以穩定重現**（「程式可以跑」不等於結果固定：外部 API、時間、競態、亂數種子、不穩定的測試都是程式跑的，卻未必穩定）（程式測試、schema validate、遷移對帳腳本、設定檔檢查、CLI 雙版本對照），加上 Harness 自己的零件（Gate 規則、追溯關係、證據新鮮度）。
  - **較弱**：要靠 agent 判斷、結果不固定的（skill／prompt 的行為評測、審查）。可以走流程拿到 PASS，但宣稱邊界要寫明「在這些情境、這個模型、這些執行條件下」。
  - **只提供流程**：沒有外部 oracle 的（研究結論、設計品味）。
- 原則：**流程支援可以很廣，強保證可以很窄，兩者不必綁在一起。**
- 第二步很可能會發現，決定保證強弱的不是單一一條「能不能由程式重算」，而是幾個因素一起作用：**判別力、代表性、可重現性、新鮮度、provenance／獨立性**。

## 4. Harness 自己的地基是 agent 執行的文字（待查證的風險）

> Codex 研究評論（2026-10-02）確認這個風險在**現行實作**成立：check 13 明寫沒有機制攔截「漏跑」，checks 8–12 同一邊界（`schema.yaml` 13.G CLAIM BOUNDARY；spec `tdd-evidence-contract`）。但要把**現行實作**與**規劃中的架構**分開：正式設計 §6–§7 要求 Gate 由 Harness 端的程式機械判定。第二步要分開盤點三件事：**哪些判準可機械判定、實際由誰執行、靠什麼強制**。

- verify 檢查（例如 Identity 新增的 check 13）是 agent 照文字執行的規則，Gate 也還沒變成程式；正式設計 §8 第 2 條又說 prompt 文字層的正確性不保證。
- 因此，就算使用者只寫 Python，每個 change 的「可信 Complete」底下仍墊著一層 agent 執行的文字。
- 既定方向是方向文件護欄 5「Gate 不變成 Agent prompt」：解法是把 Gate 變成程式，讓它從較弱的那一層搬到較強的那一層，而不是把 prompt 驗得更好。
- 第二步要回答：這個風險對研究優先序的影響有多大。它可能比 P2、P3 都更根本。

## 5. 驗證有效的三個條件，要分開取證（假說）

一個驗證要支持「我的改動在足以代表這個 claim 的條件下產生了預期行為，而且如果沒有產生，驗證看得出來」，需要三件證據：

1. **觀察到預期行為**（GREEN、對帳通過）：通常有證據。
2. **條件有代表性**（案例、環境足以代表 claim）：**最常沒證據**。Identity 的 22 個案例全部判對，但 I3 分支一次都沒被觸發。
3. **有判別力**（做錯時會真的失敗）：TDD 把判別力檢查內建在 RED→GREEN 流程裡；對原本就採 TDD 的任務，通常不需要另外設計一套負向對照，但 RED 本身的執行成本仍取決於測試層級（單元測試便宜，整合或端對端測試可能很貴）。其他方法要另外做「RED 等價物」（負向對照），例如對帳腳本故意刪一筆資料、評分器先用假報告證明分得出對錯。

第二步的具體題目：**每一種觀察方式的「RED 等價物」是什麼？**

## 6. 第二步的第一件事：內部證據盤點表（研究程序裁定）

這是研究順序的決定，不是 Verification Strategy 的結論。在讀任何外部資料之前，先把 repo 裡已有的紀錄整理成一張表。

> **盤點的目的不是比較哪個審查者比較強，而是辨識每一層驗證對最終交付可靠度提供了哪些不可替代、或與其他層重複的增量價值。**（防止這張表變成審查者排行榜。）
**不算 ROI**：現有資料做不出那種精準度，算了就是假精準。

| 欄位 | 說明 |
|---|---|
| 驗證層／方法 | 例如 task 審查、全分支總審、Codex 外部審、備援審查、盲測、verify 檢查、CLI 送達查驗 |
| 成本 proxy | 能取得的就記：派工次數、輪數、產生的材料量 |
| 抓到的 finding | 指到原始紀錄 |
| 嚴重度 | 🔴／🟡／⚪ 或 P0–P2 |
| 前一層是否已經漏過 | 這一層提供的是不是**增量**資訊 |
| 如果沒抓到會怎樣 | 例如會不會造成假 Complete |
| claim／oracle | 這一層要證明什麼、用什麼觀察（Codex 研究評論建議補） |
| 受測快照 | 審的是哪一版；不同快照、範圍、輪次的比較要標明 |
| 已知漏抓 | 這一層看過、但後來被別層抓到的 |
| 執行者與強制機制 | 誰跑、靠什麼保證它真的跑了 |

**記錄規則**（Codex 研究評論建議）：缺的成本資料標「未知」，不估；區分**首次發現**與**重新發現**；「增量價值」只寫成**觀察到的額外偵測**，因果結論留給有對照的比較；contract drift 研究的計數是分類單位，不是原始 finding 總數。

要回答的是：**哪些驗證層實際提供了增量資訊？** 成本效益至少要看兩邊：成本，以及風險降低或缺陷的價值。只抓到 1 個、但那個會造成假 Complete 的 finding，可能比 12 個文字問題更有價值，**不能只數數量**。

已知的資料來源（第二步開工時要先確認是否齊全）：

- contract drift 研究 §2：66 個分類單位（不是原始 finding 總數），按審查席位分類
- Identity retrospective §0、§2：派工次數；哪些錯是到 Codex 才被抓到
- retro-skill-inventory retrospective §1、§2：兩次 task 審查沒抓到、opus 總審抓到；備援文件審查第 3 輪抓到模板漏修
- 2026-10-02 本研究的審查紀錄：備援審查 3 輪（第 1 輪 1 🔴：拿非規範的 TE 當標準；第 2 輪 🟡：修正時寫錯衝突的兩端）；Codex 標準審查 1 輪 ✅（1 🟡：P1 過度宣稱）；Codex 研究評論抓到正文 7 處措辭／出處錯誤（備援 3 輪都沒抓到）——這一筆本身就是「哪一層提供增量資訊」的資料點

## 7. 盤點表之後的研究題（研究 backlog，不是順序承諾）

- Claim ↔ Oracle：「對齊」能不能被檢查、由誰檢查、在哪個 artifact 檢查
- RED 等價物（判別力）
- 條件代表性
- Assurance 分層（不同 PASS 的強度，以及決定強弱的因素）
- 驗到哪停：以 `auto-loop.md` 的審查收斂規則為基準；它管審查收斂，不管證據深度；它的數值有沒有實測依據，未查證。Codex 研究評論補充：覆蓋與收斂**單獨都不是保證的停止規則**（ID 兩位執行者一致，仍沒觸發 I3 分支）；每個停止條件之後要問「剩下的 claim 是什麼」，並分開**一致性、覆蓋、可重複性**；結果不固定的觀察要在開跑前定好試驗次數與成功標準。外部參考：Anthropic〈Demystifying evals for AI agents〉區分任務覆蓋與重複試驗、「至少一次成功」與「每次都成功」（Codex 引用，本備忘未查證，第二步讀原文）。
- 證據保存（P6）：Codex 研究評論建議把關鍵變數換成**要保存的是哪個 claim**：現在是否有效、歷史上是否發生過、事後診斷，三者分開測。新反例：I2 的重跑腳本複製的是**當下 repo 裡的 bridge**，不是當時測過的那一版（`raw/run.sh`），所以重跑方法本身沒有釘住輸入。
- 依成本訂政策：政策要怎麼寫，偏離要怎麼留紀錄
- 對照組：從 workflow-harness 已結案的 change 裡，找一個受測對象是一般程式的真實案例（需求 → 程式 → 測試 → 審查 → 完成），用同一套欄位重拆

## 7a. 外部來源的範圍（裁定，2026-10-02）

- **OPA**：從不讀改為**有限度地讀**，只查三件事：政策測試（policy testing）、覆蓋率（coverage）、負向案例（negative cases）。不讀 OPA 的其他部分。
- **Anthropic eval 資料**（〈Demystifying evals for AI agents〉等）：列為「驗到哪停」與「agent 評測的停止條件」的**指定來源**，重點是任務覆蓋 vs 重複試驗、「至少一次成功」vs「每次都成功」。
- 其餘來源維持第一步文件 §5b 的「先有問題、再找來源」。

## 8. 治理待辦（與研究結論分開，不要讓它佔用第二步）

- **`2026-08-27-brainstorm-產品承諾.md` 與 `.gitignore`**：今天討論引用了這份 brainstorm 的產品承諾（Contract Preservation、Verifiable Completion、Explicit Degradation）。工作目錄裡有一個未 commit 的 `.gitignore` 改動，正要把這個檔加進忽略清單。使用者的原則：**正式設計是唯一來源，brainstorm 可以退役**。所以要先確認關鍵決策是否已經完整寫進正式設計，再決定能不能忽略這個 brainstorm；如果還沒寫進去就忽略它，出處就會斷掉。初步查證（2026-10-02，只比對關鍵字，沒有比對語意）：三個詞在 brainstorm 出現 4 次，在已進版控的方向文件 `docs/superpowers/specs/2026-08-27-bridge-guarantee-architecture-direction.md` 出現 3 次，在正式設計出現 0 次。這只證明名稱有被承接的痕跡，不證明語意完整承接。下一步是**比對語意，不比對關鍵字**：方向文件或正式設計已經完整承接三個承諾的規範效果，brainstorm 就可以安全退役；還沒有的話，先補進正式文件，再忽略 brainstorm。
  - **結果（2026-10-02 語意比對、使用者裁定）**：三個承諾拆成 15 個語意要素，在方向文件或正式設計都有承接；brainstorm 沒被承接的只有未拍板的暫定想法（verify.md 未來多收四項，正式設計已把 verify.md 重構列為範圍外）、推理理由與審查過程紀錄，都不是決定。**裁定：brainstorm 退役**（只是不進版控，檔案仍在本機）；**方向文件也算正式來源**——G1–G3 的定義只在方向文件 §1.2，正式設計沒重述（G2 一次都沒出現），方向文件因此不可刪。
  - **刻意先不改**：方向文件承諾句（「不得靜默弱化」「必要 verification 已實際執行」）比正式設計 §8 第 4、5 條實際保證的強，兩者不矛盾、正式設計已自行收窄；等下次修訂方向文件或正式設計時，再在承諾句旁加註「強度見正式設計 §8」。
  - **轉為研究輸入**：方向文件 §4.3 的完成條件列有「required Review = PASS」，正式設計 I1–I7 沒有列審查結論本身，只把 Independent Review 列為可降級保障、Gate 檢查有沒有留痕。「審查結論是不是完成條件」屬本研究「驗到什麼程度算完成」的範圍，第二步一併處理，不另開追蹤。
- **Assurance 分層與成本政策**屬產品承諾層級，最後應該走正式設計的 §9 治理流程，由使用者拍板，不留在研究文件裡當推論。
