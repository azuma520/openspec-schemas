## 1. C1 回答了什麼：能力邊界

C1 的問題：agent 說自己做過 required verification，我們能不能不只相信它的自述，而有足夠依據知道 verification 確實發生？三輪的答案不是一道完美的 Gate，而是**能力邊界**（裁定）：

| 問題 | 結果 | 出處 |
|---|---|---|
| E1：關鍵 transition 前有沒有東西攔得住 | PreToolUse hook 可攔直接呼叫（direct-path enforcement），但間接執行可繞過，**不是不可繞過的 boundary** | C1 文件 §3.4 |
| E2：verification 本身有沒有真的執行 | 可達強度依驗證方法而不同；執行紀錄要離開受觀察 agent 的寫入範圍才算強證據；外送遙測的內容可判別性實測成立、trust boundary 只有文件支持（部分可行） | C1 文件 §3.3、§3.5 |

E2 的四點要分開守住：

1. **程式測試的優勢不是「容易證明 agent 以前跑過」，而是常常根本不用證明那次歷史執行**：Gate／獨立 runner 重新執行一次，新的結果本身就是證據。C1 文件 §3.3 已區分三件事：程式重算、重新執行一次 verification、證明某次歷史 execution 發生過——三者不能混用。另外，「CI 重跑」目前仍是【推論，未實作未實測】（C1 文件 §3.2），不寫成已確認能力。（**新**：把「讓 Gate 當執行者」與「讓 agent 的自述變可信」當成兩種機制，不放在同一條強弱軸上比）
2. **inspection／analysis／manual demonstration 即使有可信紀錄，也只能強到「required actions 發生過」**（例如指定檔案確實被讀），推不出「分析判得對」。而且要從執行紀錄判定人工驗證有沒有做，procedure 必須事先定義哪些可觀測動作算數；沒有可觀測準則，紀錄再可信也沒東西可比。（**新**：這是人工驗證要拿到較強證據時的額外成本）
3. **執行紀錄可不可信，關鍵是紀錄有沒有離開受觀察 actor 可修改的範圍**，不是有沒有 log。本機對話紀錄、Orca 擷取只算弱證據。（**支持**備忘 §3 末段「決定保證強弱的因素」中的 provenance／獨立性）
4. **誰來核對紀錄**仍未解：紀錄送到 agent 改不到的地方，最後卻仍由被檢查的同一 actor 自己核對並宣稱符合，assurance 沒有實質增加。屬後續 Gate architecture，不在 C1 解（C1 文件 §5 第 8 條）。

能力邊界的四層（**支持**備忘 §3 的候選劃線，C1 補上「執行是否發生」這一維的證據）：

- 可靠重新執行／機械結果取得強證據的；
- 只能留下 execution provenance 的；
- provenance 強不強取決於 trust boundary；
- 只能得到弱證據、不能包裝成強保證的。

## 2. 成本與階段：先用既有機制，不急著加新軸

討論中出現「依風險、開發階段、本益比調整驗證強度」，方向成立（**支持**備忘 §0「在合理的成本下，提升 AI agent 交付成果的可靠度與品質」、§1「依成本訂政策；執行者可以加嚴、不能降級；紀錄不能追認禁止事項」）。裁定：

- **先不新增「開發階段」軸。** 正式設計 §2.3 已有加嚴／放寬（change-local degradation）：加嚴直接寫；放寬必須附理由並經使用者接受。先檢驗它能不能表達「探索期先接受較弱 assurance、後續 milestone 再升高」，表達不了再談新增。
- **降低強度的決定權在使用者**：加嚴是一般 override、不需另附理由（正式設計 §2.3，仍寫在 proposal 的 Completion Contract Overrides、隨 proposal 接受流程）；執行中的 agent 可往上加嚴（備忘 §1）、也可以提出放寬建議，但不能自行降低最低要求。一句話：**cost-aware policy, not cost-decided-by-worker.**（**支持**備忘 §1）
- **「之後再驗」不能只是口頭延後**（**新**）。只能在較晚階段做的 validation／runtime observation／使用者回饋，要留下三件事：觸發條件是什麼、到時驗什麼、什麼叫通過。否則延後會悄悄變成跳過。repo 既有的載體是驗收節點（`驗收節點.md`：到期日＋驗收標準＋驗收手段，SessionStart hook 依日期浮出）；它是**日期觸發**的，觸發條件是里程碑或事件的延後驗證只能寫進描述。已查的載體（驗收節點）只有日期觸發，事件觸發的載體沒有查到【未查證其他載體】——這正是本條要防的缺口。
- 一句 guardrail（**新**）：**Verification 應該服務開發決策，而不是開發去服務 Verification。**

## 3. 「兩翻兩瞪眼」只代表執行與結果客觀

可機械執行的驗證（測試 PASS、hash 相符、命令成功）讓「有沒有執行、結果是什麼」變得客觀，**不等於 oracle 一定對準 claim**。測試 PASS 很硬，但測試有沒有真的在驗那條需求，是 C2／Claim–Oracle 的問題（C1 文件 §4 第 8 列；備忘 §5「判別力」、§7「Claim ↔ Oracle」）。不能因為某類驗證可機械執行，就把 correctness assurance 一起抬高。（**支持**）

## 4. 不說「判斷正確」，說「證據裁決、收斂、決策」

Bridge 不宣稱 reviewer／agent 會判斷正確——正式設計 §8 第 4 條本來就不保證 Reviewer／Verification judgment 永遠正確。比較準確的分法（裁定，**新**）：

| 問題類型 | 怎麼定案 | 例子 |
|---|---|---|
| 能被外部事實直接裁決 | 讓證據裁決，不靠互相說服 | 原始文件、實際 schema、真實命令結果、fixture、重跑實驗 |
| 有客觀 contract、但需要語意判斷 | 不同 reviewer／agent 依 contract、證據、反例審查並收斂；目標是處理掉重要異議與反例，不是證明絕對正確 | 文件審查、需求是否被做弱 |
| 設計取捨、成本效益、風險接受 | 多方觀點與證據支持收斂，由有決策權的使用者拍板 | 要不要補機制、保證要承諾到哪 |

一句話：**能被現實裁決的問題，就讓證據裁決；不能被現實直接裁決的問題，就靠多方審查收斂，再由責任人決策。**

「收斂」不是多數決，也不保證不會一起錯。兩個條件一起守：審查者要夠不同（不同模型、不同角色、加上使用者），以及能拿現實對照的地方仍要回去查原文、跑一次、做負向對照。正式判斷之前，先證明判斷方法分得出已知的正、反例（**支持**備忘 §5「評分器先用假報告證明分得出對錯」）。但 C1 第三輪也顯示這一步的限制（**新**）：**自己做的假樣本會和判斷者共用同一個錯誤假設**，自檢全過不代表判斷者對準真實資料；還需要至少一筆**已知為正的真實樣本**來對照。

當日實例（C1 第三輪）：

- 判讀腳本照錯誤的欄位讀遙測事件。開跑前的假事件自檢 6 組全過——因為假事件也是照同一個錯誤欄位做的；讓它浮現的是**已知為正的真實 session 被判成沒讀**（證據包 `./evidence/2026-10-06-c1-telemetry-execution-probe/PROVENANCE.md`「判讀腳本的版本」）。
- 研究文件一度把原因寫成「官方文件寫錯欄位」；兩位審查者中一位沒抓到、一位抓到（2026-10-06 對話中的審查紀錄，repo 內未保存審查報告）；最後定案的不是誰說服誰，而是下載官方文件原文對照（C1 文件 §3.5.2「判讀腳本的版本」）。

#### B-1 估價：四種強度各需要什麼最低證據（2026-10-07）

本節先回答「研究缺口哪一項真的會改變決策」，再決定要不要補；不是看到缺口就全部補。第 8、9、10 條指 C1 文件 §5 的編號。

| 強度 | §2.2 會怎麼寫 | 最低證據 | 第 9 條（T2 trust boundary） | 第 10 條（第二個 runtime） |
|---|---|---|---|---|
| **甲** 不進表 | 維持現狀，§8 第 5 條照舊不保證 | 不需補 | 不影響 | 不影響 |
| **乙** degradable，Gate 只檢查有沒有留下紀錄 | 有能力就留紀錄，沒有就留 degradation record；明寫紀錄是否防竄改未實測 | T1 內容可判別性（第三輪已實測成立，限制見下） | **不影響** | 只影響措辭不得綁定某一產品；文件層對照即可 |
| **丙** degradable，但宣稱紀錄比 Agent 自述可信 | 有能力時 Gate 承認它是較強證據 | 加上 T2 實測（agent 改不到外送紀錄、managed settings 蓋掉開發者設定）與收集端能辨認事件來源 | **會左右決策** | 文件層對照 |
| **丁** required | 沒有能力就 BLOCK | 丙的全部，加上「誰核對紀錄」（第 8 條）有答案 | **會左右決策** | 需要；否則等於只支援單一 runtime |

- **乙有前例**：§2.2「Verification executor independence」一列就是在 provenance 載體未實測時列入，條件是寫明「v1 Gate 對本列只判得動留痕，不宣稱判得動獨立性本身」（正式設計 §2.2 表第二列，2026-09-23 拍板）。乙沿用同一模式，不是新開先例。
- **丙、丁另外卡在第 8 條**：紀錄放對地方，最後仍由被檢查的同一 actor 核對，assurance 沒有增加。第 8 條隨 C1 凍結，也不在本備忘 §6 列的「推進 B 前要重開」清單上；所以只補第 9 條，丙、丁仍不能拍板。
- **成本估計**【估計，未實測】：第 9 條最低要把收集端放在 agent 碰不到的位置（另一個 OS 帳號或遠端）、以 managed settings 蓋掉開發者設定（Windows 上可能需管理員權限【未查證】）、確認收集端能拒收 agent 自送的假事件，估半天以上且要動系統層設定。第 10 條文件層對照估 30–60 分鐘：本機 Codex CLI 0.159.3 執行檔內可搜到 `codex.tool_result`、`codex.tool_decision`、`codex.user_prompt` 等事件名稱字串與 otel 設定字樣（2026-10-07 以 `grep -a` 搜執行檔；不是文件，事件是否帶檔案路徑、如何開啟【未查證】）。

**乙所依賴的證據的限制**（C1 文件 §3.5.2）：每案只跑 1 次、單一 runtime（Claude Code 2.1.290、Windows）、巢狀 `claude -p`；「讀過」只認 `Read` 工具成功，Agent 用 Bash `cat` 讀檔會被判 `NOT_READ`（假陰性，未驗證）；T2 未實測。

#### B-2 v1 的 Gate 範圍：只檢查紀錄存在與格式（裁定，2026-10-07）

- v1 Gate 檢查是否有留下所要求類型的 execution record，以及基本格式／必要欄位是否存在；**不解析 record 內容**去判斷 procedure 規定的 actions 是否真的發生。
- procedure **可以描述**什麼 execution evidence 對 reviewer 有意義；但 v1 Gate **不負責理解或比對**這些內容。理由：比對內容就要定義 observable action、runtime adapter、事件格式與判讀規則，等於往丙的方向走，並把第三輪單一 runtime、每案 1 次的實驗直接升格成產品規則。
- **內容比對不屬本次 Decision B 的 v1 裁定；若未來要加入 Gate，另立設計決策。**（不因為進入正式設計階段就順帶納入。）

#### B-3 乙相對甲的收益（成本衡量結果見 B-6）

- 審查者多一份**由執行環境產生、與 Agent 的 verification 結論分離**的對照材料。它的價值是多一個不同來源的觀察面，**不是**已證明不可偽造——C1 已確認本機紀錄 agent 改得到（C1 文件 §3.5.1），v1 也不宣稱 trust boundary 成立。第三輪「沒讀卻宣稱 PASS」的對照案例說明這種材料可能揭露自述與實際動作不一致（C1 文件 §3.5.2）。
- 能力缺失會**顯式降級**（留 degradation record），而不是讓使用者誤以為 execution evidence 存在。
- 這兩項收益值不值得付實作成本，由正式設計變更衡量；本備忘不先認定一定值得。（2026-10-07 盤點：兩項收益在 Gate 出現前都兌現不了，見 B-6。）

#### B-6 正式設計盤點：現在不實作，與 Completion Gate 落地一起重新評估（使用者 2026-10-07）

B-4 排定的正式設計變更，先盤點三題（能力定義／v1 Gate 判到哪／乙相對甲值不值得）再決定要不要開 change。盤點只讀既有文件，沒有新實測。

**盤點發現**：

1. **能力定義**：措辭可沿用 §2.2「Verification executor independence」一列的模式（B-1 已述）。但寫成條文前有三題 B-1～B-5 都沒回答：
   - **證據落點和正式設計 §3.4 衝突**：§3.4 規定長證據須是 repo 內已 commit 的檔案，scratchpad、git-ignored、未追蹤檔一律不得作證據落點；系統寫的紀錄都在 repo 外（本機對話紀錄在使用者家目錄，遙測在外部收集端）。複製進 repo 就成了 agent 製作的副本（正式設計 §1 上位原則「結構化副本仍是副本」），只引用 repo 外位置則不符 §3.4。
   - **隱私**：C1 實測的遙測事件每筆都帶帳號屬性（email、account id），證據包是刪除後才保存的（C1 文件 §3.5.2）；本 repo 公開，紀錄若要 commit 須先決定去識別化。
   - **適用哪些驗證方法**：裁定前題目（本節開頭）列為必答，未決。
2. **v1 Gate 判到哪**：裁定已定（B-2），但正式 Completion Gate 尚未實作——只有 PoC `gate_check.py`，未接進任何流程（C1 文件 §1.2）；archive 前的宿主／攔截點未定（C1 文件 §4 第 4、5 列）；工作地圖沒有任何 Gate 實作的工作（2026-10-07 查）。不等 Gate 的唯一做法是比照 Identity check 13 寫成 verify 階段由 agent 執行的規則，結果是 agent 檢查自己有沒有留紀錄，而降級紀錄本來就由 agent 寫。
3. **乙相對甲的收益**：B-3 的兩項收益在 Gate 出現前都兌現不了——對照材料要有流程讓人去讀，v1 又不比對內容；顯式降級要有東西檢查降級紀錄存在。成本卻要現在付（落點、隱私、適用方法、schema 改動），並碰上 Identity 否決過的路（先寫一支像 `gate_check.py` 的腳本會長成半套 traceability system，`openspec/changes/archive/2026-10-01-requirement-scenario-identity/design.md` D6）。

**裁定（2026-10-07，使用者）**：選「暫不實作、正式延後」。execution-record capability 暫不進 §2.2、不進 schema；B 的乙（B-1、B-2）保留為**未來若納入時**的 v1 assurance boundary。新增 Completion Gate 落地工作作為明確觸發點，execution-record capability 依賴它。也考慮過、未選：現在只改設計文件在 §2.2 加一列（寫這列就得先解落點與隱私）；現在就實作成 verify 階段由 agent 執行的檢查（增加 schema 複雜度，assurance 幾乎不增加）。

- **「值得存在」與「現在值得實作」是兩個問題**：B（2026-10-07 研究層裁定）回答前者——若納入，v1 做到乙；本次盤點回答後者——目前沒有任何下游機制會消費這份 evidence，不值得單獨實作。這不推翻決策 B，而是完成 B-3 原本保留的成本效益判斷。是 §2「Verification 應該服務開發決策，而不是開發去服務 Verification」的具體案例。
