### 【Harness 系統治理與決策判準｜討論回顧】

討論期間：2026 年 8 月 25～26 日前後

這次討論的核心，其實不只是如何設計 Harness 系統的護欄，而是更根本的一個問題：

當系統出現問題、風險或改善需求時，我們應該如何判斷「值不值得處理、需要處理到什麼程度，以及用什麼方式處理」？

我們希望建立的不是一套遇到問題就增加規則的系統，而是一套能夠根據證據、風險與成本，選擇適當改善手段的決策機制。

先說明資料範圍：目前找到了當時的《2026-08-26 監督式協調攜出討論包》，以及先前討論留下的四維度判準摘要。以下會將兩者整合，但不把後來的整理當成當時已經正式定案的規格。

#### 一、討論起點：為什麼我們需要這套判準？

當時 Harness 系統已經逐漸形成一套具備規則、驗證、交接及多代理協作能力的開發環境。

但隨著機制增加，也浮現另一個問題：

我們是不是可能為了避免某種錯誤，而建立了成本遠高於實際風險的防護措施？

例如，某個 Agent 曾經因為委託資訊不完整而出錯。

直覺上的處理方式，可能是增加審查程序、加入新護欄，甚至要求每次派工都經過多重確認。

然而，這裡有幾個問題值得先想清楚。

這個錯誤經常發生嗎？造成的實際影響有多大？是不是派工機制本身導致的？有沒有更簡單的方法可以避免？

如果這些問題都還沒釐清，就直接增加制度，我們可能只是在不斷累積維護成本。

因此，討論逐漸轉向：

> 不是看到問題就增加防護，而是先判斷問題的性質，再決定投入多少改善資源。

#### 二、四個核心判斷維度

這裡要區分兩個版本。

當時較早的四維度摘要是「頻率、影響程度、可恢復程度、改善成本」。

你後來記得的則是「頻率、風險、可歸因、投報」。

兩者可以互相連結，但不能視為完全相同。尤其「可歸因」是用來檢查問題成因的，而「可恢復程度」是用來衡量出錯後的損害，兩者扮演不同角色。

以下依照我們現在重新整理的邏輯呈現。

- **頻率｜問題是不是常態？** 先區分偶發事件、重複事件，以及系統性的缺陷。偶爾發生一次，不代表需要建立永久護欄。
- **風險｜不處理的代價有多大？** 不只看發生機率，也看影響範圍、損失程度，以及事後能否恢復。有些錯誤即使少見，仍值得優先防範。
- **可歸因｜是否確認真正原因？** 確認問題到底來自機制、執行方式、委託內容，還是人為判斷。原因不明時，改善方案就只能當成假設。
- **投報｜這樣改善划算嗎？** 比較改善後能降低多少風險，以及開發、執行、維護所需的成本。優先尋找成本低、但足以解決問題的方法。

這四個維度適合形成一個決策流程，但它們還不是經過驗證的數學評分模型。

尤其「風險」與「頻率」存在部分重疊，因此不宜直接把四項分數相加。

#### 三、當時討論中最有代表性的實際案例

**案例 A：檔案撞號，卻錯怪派工模式**

當時有兩條並行工作線，各自取得相同的 Backlog 編號，造成撞號問題。

一開始，我們將這個問題歸咎於派工方式。

但後來追查發現，真正的原因是兩條獨立工作線都會修改同一份共用檔案。

也就是說，即使換一種派工模式，問題可能仍然存在。

真正有效的改善方式，是在派工前就分配好編號，並寫進委託內容。

這個案例帶來的重要教訓是：

發現錯誤，不等於已經知道造成錯誤的原因。

如果歸因錯誤，不但無法解決問題，還可能增加不必要的制度。

**案例 B：監督式協調真的有必要嗎？**

2026 年 8 月 23～26 日，我們曾對監督式協調進行四天實際測試。

當時最重要的發現之一，是執行 Agent 多次攔截協調者提出的錯誤前提。

例如，協調者判錯稽核範圍、委託內容存在矛盾，或是執行者發現原先提出的問題成因根本不正確。

這顯示監督式協調有一項重要價值：

執行者不只是完成任務，也能在發現上游判斷錯誤時，將問題送回協調者。

但我們並沒有因此直接認定所有任務都需要監督式協調。

因為還有另一個問題：能否透過更好的委託文字、事前審查或簡化回報機制，取得相近效果？

這就是「風險」與「投報」之間的取捨。

**案例 C：原本以為很貴，實測卻不是**

另一個具體例子，是同一件工作曾出現三組耗時資訊：最初估計 20–40 分鐘、第二次估計 69 分鐘、實際執行 24 分鐘。

其中最不準確的 69 分鐘估計，反而造成協調者額外停下來詢問使用者。

這讓我們注意到：高估改善成本，也可能讓系統放棄原本值得執行的工作。

因此，在資訊不足時，不一定要花很多時間推估成本，也可以考慮先做小規模測試，再根據真實數據決策。

上述案例及實測數字，均出自當時的監督式協調討論包。

#### 四、當時逐漸形成的治理原則

我認為可以整理成三個層次。

第一層：先確認事實，不急著修正。

當發現問題時，先收集實際案例、發生條件、影響程度與相關證據。

如果原因還不明確，就保留假設，而不是直接把推論當成事實。

第二層：選擇必要且充分的改善方式。

確認問題後，先問能否透過較小的調整解決。

例如，修改委託文字就能處理的問題，不一定需要額外開發新的監督模組。

但如果風險很大、難以恢復，即使發生次數不多，也可能需要更強的預防機制。

第三層：改善後還要驗證。

改善方案完成，不代表問題已經解決。

我們仍需要觀察錯誤是否減少、新增成本是否合理，以及有沒有產生其他副作用。

這也延伸出一個很重要的概念：

> 護欄的價值，不在於建立了多少規則，而在於它是否以合理的成本，降低了真正值得防範的風險。

#### 五、討論後來延伸到「派工模式的選擇」

當時的討論不只停留在一般風險治理，也延伸到一個具體問題：

什麼情況應該讓 Agent 獨立完成，什麼情況需要監督式協調？

8 月 26 日的文件記錄了一套尚未拍板的 V3 判準。

- 多項任務需要整合嗎？不需要 → 各自獨立完成，採完全交接；需要 → 先判斷能否由一個 Agent 整包完成。
- 確實需要拆分且並行處理：任務可預測 → 可批次派出、統一回收結果；存在不確定性 → 保留中途問答與決策機制。
- 不論採用哪種模式，共用檔案都需要事前分配寫入責任。

當時還發現一個值得補充的問題：

「協調者對自己提出的任務前提，究竟有多少把握？」

因為 Agent 不一定是執行能力不足，也可能是協調者一開始就交代錯了方向。

這讓監督機制的價值，從單純的「管理複雜任務」，延伸到「容許下游反過來修正上游的判斷」。

不過文件也明確指出，當時缺少公平的對照測試，尚不能認定監督式協調一定優於完全交接。

#### 六、當時尚未完成的部分

有三件事情還需要保留。

一、四維度尚未形成正式決策規格。 我們有了判斷方向，但沒有證據顯示已經正式確立固定的計分方式、權重或門檻。

二、監督式協調的成本效益仍待驗證。 當時有實測案例支持其價值，但尚缺乏相同任務條件下的公平比較。

三、改善成本的計算還不夠完整。 文件指出，過去某些分析只計算人員花費時間，沒有完整納入機器執行時間與長期維護成本。

因此，這套方法比較適合視為正在成熟的決策框架，而不是已經驗收完成的系統。

#### 七、重新歸納這次討論的核心思想

綜合這些紀錄，我會把我們當時想建立的能力，整理成下面這個循環：

1. 觀察問題：收集事件與實際證據
2. 評估風險：判斷頻率、影響與可恢復性
3. 確認歸因：區分真正原因與暫時假設
4. 選擇改善：比較效益、成本與替代方案
5. 驗證結果：檢查改善是否有效，再決定是否制度化

這是我根據討論脈絡重新整理的流程，不是當時已正式核定的流程圖。

我覺得最值得留下的一句話是：

「不要只追求系統不犯錯，而是讓系統有能力判斷哪些錯誤值得預防、哪些問題值得改善，以及改善到什麼程度才合理。」

這其實已經超出 Harness 的範圍。它可以運用在 Agent 開發、工作流程改善、系統維護，甚至一般管理決策。

而且還有一個值得繼續研究的方向：當我們把這套判準做成 Skill 時，應該讓它輔助決策，而不是每次遇到問題都強制啟動一套繁重的評估流程。

這才比較符合當時討論中「必要且充分」的精神。

## 2. 用意（AI 的理解，使用者 2026-10-12 確認）

**一句話：看到問題不先加規則，先判斷值不值得處理、處理到什麼程度、用什麼方式處理。**

| 維度 | 問什麼 | 防的是什麼 |
|---|---|---|
| 頻率 | 偶發還是會一再發生？ | 為一次性事件建永久護欄 |
| 風險 | 不處理的代價多大、事後能不能補救？ | 忽略少見但無法補救的錯 |
| 可歸因 | 真正原因查清了嗎？查清的是事實，沒查清的只能當假設 | 改錯地方：撞號怪派工模式，實際是共用檔案 |
| 投報 | 能降多少風險、要花多少（開發、執行、維護，也要算機器時間）？最小而足夠的改法是什麼？ | 用重型機制處理輕型問題；以及高估成本，害人放棄該做的事 |

用法上的三點：

- 四個維度是**提問**，不是打分數。頻率與風險有重疊，不加總。
- 改完要**回頭驗證**：錯誤有沒有變少、成本合不合理、有沒有副作用。有效了才考慮制度化。
- 和既有規則同一精神：全域 CLAUDE.md「收工前：學習候選」規定，新增一條規範必須寫出它的 enforcement 掛點，也就是不照做時誰會發現、哪一層會喊；寫不出來就降級成 Observe。這可以看成「投報」的一條硬條件。
