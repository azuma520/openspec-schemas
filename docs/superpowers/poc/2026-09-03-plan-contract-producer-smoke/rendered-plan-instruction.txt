plan.md is a per-task execution contract: each entry states what
"done" means for one task, not how to get there. Two executors may
satisfy the same entry by different paths and both conform.

STRUCTURE — a header, then exactly one entry per tasks.md task.

1. Header
   - Goal: what this change delivers, in one or two sentences.
   - Pointers: this change's specs/ files and design.md. Reference
     architecture and tech-stack decisions there; do not repeat
     them here.
   - Global constraints: copied verbatim from the specs, stated
     once, binding on every entry below.

2. One contract entry per task in tasks.md, keyed by the tasks.md
   task number (1:1 — the set of entry keys and the set of task
   numbers must be identical in both directions; a task with no
   entry and an entry keyed to no task are both defects). Write
   each entry as a `##` heading whose text BEGINS with that task
   number, e.g. `## 1.1 — Login error handling`; the title after
   the number is free. The key must LEAD so the entry-key set is
   readable without interpretation — verify's deterministic
   key-set check reads exactly this form. A `##` heading that
   does not begin with a number is not an entry (this plan's own
   header, a self-review section). Each entry states:

   - Delivers — the end-to-end behaviour this task produces, not a
     layer-by-layer implementation list.
   - Acceptance criteria — concrete and verifiable. Vague language
     such as "works correctly" or "handles errors appropriately"
     is non-conforming: someone who did not write the entry must
     be able to check the criterion and reach the same answer.
   - Blocked by — the tasks that must land first, or an explicit
     "none".
   - Interfaces — CONDITIONAL. Required only where the task
     couples with another task: the names and shapes it consumes
     or produces, and which task sits on the other end. Omit it
     for a task with no cross-task coupling; do not invent one to
     fill the field.

RIGHT-SIZING: one entry per task, and a task is the smallest unit
that carries its own verification cycle and is worth a fresh
reviewer's gate — sized to fit a single fresh context window.

WHAT NOT TO WRITE: do not decompose entries into micro-steps and
do not prescribe an execution sequence. Exact file paths, code
snippets, test commands and commit points are NOT required —
implementation detail goes stale fastest, and prescribing it takes
ownership of the path away from the executor. A decision-rich
snippet (state machine, schema, type shape) MAY be included where
it encodes a decision more precisely than prose can.

TDD stays in tasks.md: the applicability annotation and the
RED/GREEN evidence live under the task checkboxes there. An entry
MAY echo a task's applicability but MUST NOT redefine it, and
plan.md MUST NOT hold a second copy of the evidence.

SELF-REVIEW before you finish. This is generation-time feedback,
not the required control: the required control is the verify
artifact, whose deterministic checks are run before archive and
block on failure. That enforcement is instruction-mediated — an
agent following the verify instruction — not a mechanically
enforced gate, so passing this list is not a guarantee.
1. Entry keys — does the set of entry keys equal the set of
   tasks.md task numbers exactly, in both directions?
2. Acceptance criteria — is every one of them checkable by someone
   who did not write it? Rewrite any that are not.
3. Interfaces — does every task that couples with another task
   state its interfaces, and does each side name the other?
