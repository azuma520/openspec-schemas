## 4. 為什麼 A1/A2/A3 測不出差異 —— 逐案 provenance

六個輸入取自過去的 review finding，而**那些 finding 各自在不同時間、由不同 commit 修掉**。
初版把它們一律歸給 `e38e817` 是錯的。

| 案例 | 決定它的規則 | 引入 commit | 日期 |
|---|---|---|---|
| I1 兩行 `subject:` | `FIELD CARDINALITY`、`A FIELD IS EXACTLY ONE LINE` | `e38e817` | 2026-09-08 |
| I2 無 `subject:` | RED 必填 `subject:`／`outcome:`／`failure:` | **`932a044`** | 2026-09-02 |
| I3 `###` | `or deeper is a sub-heading` | `e38e817` | 2026-09-08 |
| I4 `]1.1` | `]` 後須至少一個空白字元 | `e38e817` | 2026-09-08 |
| I5 `## 1x` | entry key token 兩側界定 | **`4626e96`** | 2026-09-14 |
| I6 圍籬 | **無** —— 從未被規定，policy gap | — | — |

```
932a044  2026-09-02  feat(schema): plan becomes a contract, TDD becomes evidence (v1 -> v2)
e38e817  2026-09-08  fix(schema): close the code-plane review findings and land the verify artifact
4626e96  2026-09-14  fix(schema): reconcile check 2 with check 7's deferred-task rule
```

**結論的方向不變**：A1 對這六案都是**修正後**的文本，天花板效應成立。
**但機制不是「同一次修正」**，而是「三次不同的修正，各自蓋掉其中一部分」，外加
一個從未被修的 policy gap。

### 可複驗（逐條單獨跑；此寫法會把 0 命中明確印出來——本表六條皆命中）

```bash
for s in "FIELD CARDINALITY" \
         "A FIELD IS EXACTLY ONE LINE" \
         "or deeper is a sub-heading" \
         "ONE whitespace character must follow" \
         "requires the fields" \
         "DELIMITED on both sides"; do
  printf '%s\n' "--- [$s]"
  r=$(git log --oneline -S "$s" -- superpowers-bridge/schema.yaml | tail -1)
  [ -z "$r" ] && echo "    <<< 0 命中 >>>" || echo "    $r"
done

# I6 那一列（「無 —— 從未被規定」）沒有規則字串可查，改以缺口掃描複驗：
grep -ciE "fenc|code block|backtick|<!--" superpowers-bridge/schema.yaml   # 預期 0
```

⚠️ 初版寫的搜尋字串 `AT LEAST ONE whitespace character must follow` 在原檔**跨兩行**，
逐字查回 **0 命中**。初版把多條查詢並排成一張表，空輸出被下一列的標籤接上，因此被
誤讀為命中 `e38e817`。上面的寫法一條一行、並把 0 命中明確印出來，正是為了讓這種

## 5. Arm 0 回答了什麼、沒回答什麼

### ⚠️ 用途界線（先寫，避免被誤讀）

Arm 0 與 Arm 1 之間**不只表達形式不同，規則內容本身就變了**。因此：

> **Arm 0 → Arm 1 的任何差異，MUST NOT 歸因給「結構化」。**

Arm 0 只回答一個問題：**這六個案例對歷史上真正出問題的規則版本，有沒有辨識力？**

### 回答：有，而且是兩種不同的失敗形狀

**I1（兩行 `subject:`）→ UNDETERMINED。** 這是整個實驗 24 格裡**唯一**的
UNDETERMINED。讀者給的理由是：check 11 要收「每筆 RED 紀錄的 `subject:` 值」，
但「規則文字從未指明一筆紀錄帶多個 `subject:` 時該用哪一個值、或怎麼用」。
**那正是 FIELD CARDINALITY（`e38e817`）當初被加進去要解決的事。**

**I4（`- [x]1.1 Foo`）→ PASS，修正後 → BLOCK。** 修正前沒有「`]` 後必須至少一個
空白」那條（同樣來自 `e38e817`），讀者於是把它讀成任務編號 `1.1`、與 plan 的 `1.1` 對上。

**I5（`## 1x`）→ PASS，修正後 → BLOCK。** 修正前沒有 token 兩側界定規則
（來自 `4626e96`，2026-09-14），讀者取了前導 `\d+` 得到 key `1`、把 `x` 忽略。

I4 與 I5 這兩格**都不是判不出來，是很有把握地判錯**（相對於後來確立的意圖）。

**I2 → BLOCK，與修正後一致。** 合理：該規則自 `932a044`（v1→v2）就已存在，
`e38e817^` 的文本已經有它。這格本來就不具辨識力。

### 所以能說什麼

- ✅ 這六個案例**不是送分題**——其中三格能區分「修正前」與「修正後」的規則。
- ✅ **修正規則內容是有效的**：三格分歧分別被 `e38e817`（I1、I4）與 `4626e96`（I5）消除。
- ❌ **不能說「散文比較差」**：A1 本身就是散文，而它 100%。
- ❌ **不能說「結構化有幫助」**：A2/A3 與 A1 同分，且三個 Arm 並非嚴格等價（§6）。

### 對 Q8 原假說的影響

Q8 原本的假說是「結構化表示可以降低判讀歧義」。**本輪未能檢驗它**——兩個獨立原因：
修正後的散文已把這六案的歧義消乾淨（天花板效應），且三個 Arm 並非嚴格等價（§6）。

這**不等於**假說被推翻，也不等於它獲得支持。

## 6. 實驗設計缺陷（experiment design defect）

外部文件審（Codex，2026-09-21）推翻了本實驗「A2/A3 只是 A1 的重新表達」這個宣稱。
以下四處偏離經覆核屬實：

| # | 偏離 | A1 怎麼說 | A2/A3 怎麼寫 |
|---|---|---|---|
| D1 | `outcome:` 值的空白處理 | GREEN 須**恰為** token `PASS`；RED 須為**不含空白**的單一大寫 token | V2/V3 對 `trim(v)` 判定 → **接受 A1 會擋的前後空白** |
| D2 | 畸形 TDD 標註 | 「零行、超過一行、**其他形式**」皆 BLOCK | A3 的 P1 只數**合法**的 TDD 行 → 一個合法＋一個畸形 ⇒ `|A|=1` ⇒ **不報 F8** |
| D3 | checks 9-11 的適用條件 | 不以 check 8 是否通過為前提 | A3 的 P2 要求 `|A(t)|=1` 才進 `APPLICABLE` → **新增了 A1 沒有的閘** |
| D4 | plan.md 缺席時的重複掃描 | 兩側**各自獨立**檢查、且 stage one **不短路** | A3 的 P8 把 `TN` 重複掃描放在「plan.md 存在」分支內 → **plan 缺席時漏報 tasks 側重複** |

D1 同時影響 A2 與 A3（兩者共用 PART I）；D2、D3、D4 只影響 A3 的判定程序。

**D5（不影響判定，但仍是差異）**：A1 把共用定義段的射程寫成
`used by checks 8-11`（`schema.yaml:561`），而 A2/A3 的 PART I 呈現為 checks 8-**12**
共用——**等於默默修正了 §7.3 記錄的那個射程錯誤**。它不改變本輪任一格的判定
（各 Arm 的 check 12 都自帶取鍵規則），也不是規則內容差異，故與 D1–D4 分開列。
由 2026-09-21 的 fallback 文件審指出。

## 7. 三個實質發現

### 7.1 判定相同，依據不同 —— 而三個指標都抓不到

| 輸入 | A1 走的條款 | A2 走的條款 | A3 走的條款 |
|---|---|---|---|
| I4 | stage-two 集合差異 | stage-two 集合差異 | `F12_no_number` |
| I5 | stage-two 集合差異 | 「plan 存在但收不到 key」＋集合不等 | `F12_no_keys` |

三條路徑在這兩個輸入上**都成立**，沒有人判錯。但這代表
**verdict 一致 ≠ 理解一致**。只要出現一個「只滿足其中一條」的輸入，這些讀者就會分岔。

更要緊的是：checks 的契約明文要求**回報每一條 finding，不是只報第一條**
（`schema.yaml` 反覆出現 `every one that holds is reported, not just the first`）。
本實驗只收 `PASS / BLOCK` 加一句依據，**量不到 finding 集合是否相同**。

**記為 experiment specification defect。** 下一輪若還研究這題，指標必須收
**verdict ＋ 觸發的 finding 集合 / rule ID**。

### 7.2 policy gap 會靜默產生確定答案 —— `UNDETERMINED` 不是完整的缺口偵測器

I6（圍籬內 `- [x]`）：**四個 Arm、四位讀者，全部判 BLOCK，零 UNDETERMINED**，
理由一致——圍籬裡那行在文字上就符合 task line 樣式，而規則沒有任何一句排除圍籬
（`schema.yaml` 全檔 grep `fenc|code block|backtick|<!--` 零命中）。

依事前登記，這格的 Correctness 不計分，且不得讀成任何 Arm 的改善或失敗。

> **缺一條政策，不會表現成「判不出來」，會表現成「安靜地給出一個沒人決定過的答案」。**

A0_I4 / A0_I5 是同一現象的另一半：規則不足時，讀者同樣沒有喊 UNDETERMINED，
而是很有把握地給了一個（相對於後來意圖）錯的答案。

**推論**：24 格裡規則確有缺口的場合共 **7 格**（I6 × 4 ＋ A0_I1 ＋ A0_I4 ＋ A0_I5），
其中只有 1 格喊了 UNDETERMINED。
（初版寫「至少 5 格」，漏計了上一段才剛認定為同一現象的 A0_I4 與 A0_I5，已更正。）

**現況佐證**：掃描 `superpowers-bridge/templates/**/*.md` 全部 10 份範本，
**圍籬區塊內的 task line 數 = 0，HTML 註解區塊內的 task line 數 = 0**。
故 bridge 自己的範本**沒有**踩到它。缺口為真，活體實例為零。
（初版只引了 `templates/tasks.md` 的兩個 `<!--` 區塊——那只證明了註解那一半，
而「它」在上一段定義的是**圍籬**缺口。圍籬掃描是補做的。）

### 7.3 `Shared definitions, used by checks 8-11` 的射程是錯的

`schema.yaml:561` 宣告這些定義供 checks 8-11 使用，但 check 12（`:787`）就在用
`TASK LINE`。**名字說 8-11，實際含 12。** 此錯誤**在 `e38e817^` 就已存在**。

依 `pre-registration.md` §結論邊界第 2 條，這是 finding，**不進三個指標**，本輪不修。
