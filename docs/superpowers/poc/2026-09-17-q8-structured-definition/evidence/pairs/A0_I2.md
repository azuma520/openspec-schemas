# tasks.md / plan.md 驗證規則

```text
      CHECKS 8-12 — TDD EVIDENCE CONTRACT AND PLAN/TASK KEY SET.
      These five are DETERMINISTIC: each decides its verdict by
      reading text against a fixed rule, with no judgement call. The
      `tasks` artifact's instruction is the definition of the
      annotation grammar and the record shape; these checks read
      exactly that grammar and add nothing to it.

      Shared definitions, used by checks 8-11:

      - A TASK LINE in tasks.md is any line whose first non-space
        characters are `- [`, one character, `]` — `- [ ]`, `- [x]`
        and `- [~]` alike. Let N be that line's indent (its number of
        leading spaces).
      - A line BELONGS TO that task when it comes after the task line,
        before the next task line or `#` heading whose indent is <= N,
        and its own indent is STRICTLY GREATER than N.
      - BLANK LINES ARE TRANSPARENT. A blank line belongs to nothing
        and ends nothing: skip it and keep reading. A task's range
        ends at the next NON-BLANK task line or `#` heading whose
        indent is <= N, or at the end of the file.
      - INDENT RULE — any indent strictly greater than N is accepted.
        The `tasks` instruction tells authors to write two spaces, and
        the templates show two; this check does NOT require that
        depth. The contract's obligation is nesting, not a column
        count, so a conforming tasks.md that a formatter re-indented
        must not be blocked for the width of its indent.

       8. **TDD annotation present and well-formed** (deterministic):

          For EVERY task line in tasks.md, exactly one line belonging
          to it must match, after its indent is trimmed, one of these
          two forms — the leading `- ` IS part of the required form:

            - TDD: applicable
            - TDD: n/a <SEP> <reason>

          <SEP> is one of `—` (em dash, canonical), `–` (en dash), `-`
          (hyphen), or `--`, and nothing else; the obligation is a
          non-empty <reason>, not a particular character. Zero
          matching lines, more than one, any other form, or an `n/a`
          whose reason is empty after trimming → BLOCK.

       9. **RED and GREEN records present, required fields present
          and non-empty, and every `subject:` value well-formed**
          (deterministic):

          For every task annotated `TDD: applicable`, the lines
          belonging to it must include AT LEAST ONE `- RED:` line and
          AT LEAST ONE `- GREEN:` line. This check decides PRESENCE:
          how many records a task may carry, and how they pair, is
          check 11's question — no sentence here presumes a single
          RED or a single GREEN. Let R be a record line's indent; a
          FIELD of that record is a line written `- <key>: <value>`
          that comes after it with indent strictly greater than R,
          before the next NON-BLANK line whose indent is <= R (the
          same nesting rule, one level deeper — again any greater
          indent, not a fixed width, and again blank lines are
          transparent: a blank line between two fields does NOT end
          the record. A record hand-formatted with spacing is
          conforming; nothing extra is picked up either way, because
          the field keys are literal).

          `- RED:` requires the fields `subject:`, `outcome:` and
          `failure:`. `- GREEN:` requires `subject:` and `outcome:`.
          `invocation:` is supporting evidence and is never required.
          EVERY record belonging to the task is examined: a defect in
          a task's second RED record is reported exactly as one in its
          first.

          SUBJECT GRAMMAR — a `subject:` field is satisfied when it
          is present AND its value conforms to the grammar below; a
          `subject:` whose value fails that grammar is NOT a satisfied
          field, and this check reports it. No other field has a
          grammar here. Take the value with leading and trailing
          whitespace trimmed, and scan it left to right for the
          two-character sequence `::`, consuming each match as it is
          found so that matches never overlap (`a:::b` therefore holds
          ONE such sequence, not two). The value conforms when it
          holds EXACTLY ONE such sequence AND the remainder on each
          side of it is non-empty after trimming. NOTHING FURTHER is
          constrained — not path syntax, not file extension, not the
          characters of the test name — so
          `tests/api_test.go::TestRejectsEmptyEmail/subcase-2` and
          `a:::b` both conform, while `rejects empty email` (no
          sequence) and `a::b::c` (two) do not.

          A task annotated `TDD: n/a` owes no records; if it carries
          them anyway, checks 9-11 do not apply to it — what reports
          such a task is review judgement R4, never a check. A missing
          record, a missing required field, a required field whose
          value is empty after trimming, or a `subject:` value that
          fails the grammar → BLOCK, naming the offending value and
          the record it belongs to. Every such finding is reported,
          not just the first.

      10. **Outcome markers** (deterministic): this check reads the
          MARKER ONLY — whether a RED `failure:` excerpt is a
          behavioural failure rather than a harness error is review
          judgement R1 below, never this check. It is applied to EVERY
          record belonging to the task, however many there are. Each
          GREEN record's `outcome:` value must be exactly the token
          `PASS`. Each RED record's must be a single token of
          uppercase letters A-Z with no whitespace, and must not be
          `PASS` (`FAIL`, `ERROR`, `FAILED` all conform). Any GREEN
          outcome other than `PASS`, and any RED outcome that is
          `PASS` or does not match that token form → BLOCK, naming
          the record; every offending record is reported, not just the
          first.

      11. **Records pair by `subject:` value — unique on each side,
          then one RED and one GREEN per subject** (deterministic,
          two stages):

          Records pair by their `subject:` VALUE, never by position.
          Ordinal pairing (the n-th RED with the n-th GREEN) is NOT
          used, because inserting one record silently re-pairs every
          record after it.

          For each task annotated `TDD: applicable`, collect the
          trimmed `subject:` value of every `- RED:` record belonging
          to it as a LIST in order of appearance, and the trimmed
          `subject:` value of every `- GREEN:` record belonging to it
          as a second list. Values are compared character for
          character as opaque strings; whether a value conforms to
          check 9's grammar is check 9's finding, and a malformed
          value still takes part here — so one task can yield a
          finding from both checks, and each is reported.

          STAGE ONE — UNIQUENESS WITHIN EACH SIDE, before either
          list is reduced to a set. A value appearing more than once
          in the RED list, or more than once in the GREEN list, is a
          failure of this check on its own, whatever the other side
          holds. Report EVERY repeated value by name and by the side
          it repeats on — "`auth.test.js::rejects empty email` occurs
          twice among this task's RED records" — and BLOCK.
          Uniqueness is what makes the pairing decidable: two
          identically named subjects each carrying a RED and a GREEN
          leave no way to say which pairs with which. Re-running a
          test is not recorded as a further record: one subject
          carries one RED and one GREEN however many times it was
          executed.

          STAGE TWO — PAIRING. Now reduce both lists to sets and
          compare them in BOTH directions, reporting each difference
          individually: a subject with a RED record and no GREEN
          record, and a subject with a GREEN record and no RED record.
          Equal counts do not pass this stage — REDs `{A,B}` against
          GREENs `{A,C}` fails in both directions.

          A stage-one BLOCK does NOT end the check. Stage one does not
          short-circuit: stage two is evaluated whatever stage one
          found, and each stage reports its own findings, so an input
          carrying BOTH a duplicate and an unpaired subject yields
          both sets of findings in ONE run rather than revealing the
          second only after the first is repaired. The two messages
          are DISTINCT because the defects are: a duplicate is
          repaired by removing or renaming one record, an unpaired
          subject by supplying the missing side. A set comparison
          cannot see a duplicate at all — the set absorbs it — which
          is why this stage runs first.

          ANY of the following → BLOCK, and every one that holds is
          reported, not just the first: a repeated value on either
          side (stage one), or either direction of the set comparison
          non-empty (stage two).

          BOUNDARY OF CHECKS 9-11 — state it in verify.md as written
          here and claim no more: these three checks decide STRUCTURE,
          FORMAT and CARDINALITY only. They NEVER decide evidence
          truth. That a named test exists, that it tests the behaviour
          the task claims to deliver, that the recorded outcomes are
          the outcomes that actually occurred, and that the RED was
          obtained before the implementation, are none of them decided
          here: R1 and R2 below carry the first two as review
          judgements, and the ENFORCEMENT BOUNDARY paragraph below
          carries the rest — no result of checks 9-11 is evidence
          about any of them.

      12. **tasks.md task numbers and plan.md entry keys correspond
          1:1 — no duplicate on either side, then equal sets**
          (deterministic, two stages):

          Collect the TASK NUMBER of every task line in tasks.md: the
          token IMMEDIATELY after the `]` of its checkbox and the
          whitespace following it, when that token matches
          `\d+(\.\d+)*` — a task line whose first token there is not a
          number has no task number, and that is itself a defect of
          this check (the plan cannot be keyed 1:1 to it).
          Collect the ENTRY KEY of every plan.md contract entry. The
          `plan` artifact's instruction is what REQUIRES the entry
          form — each entry a `##` heading whose text begins with the
          tasks.md task number, e.g. `## 1.1 — <title>`; this check
          implements that requirement and introduces nothing of its
          own. So: the leading `\d+(\.\d+)*` token of each `##` heading
          in plan.md whose text begins with such a token. Headings
          that do not begin with a number (the plan header, a
          self-review section) are not entries and are not collected.

          If plan.md does not exist at all, this check fails: `plan`
          is a required artifact of this schema, so an absent plan.md
          is not a normal state and must not be read as a vacuous
          pass. Report it as "plan.md absent — no entry keys to
          compare" rather than as a set difference.

          STAGE ONE — DUPLICATES, before either collection is reduced
          to a set. Keep both collections as LISTS in order of
          appearance and examine each side INDEPENDENTLY: a task
          number carried by more than one task line in tasks.md, and
          an entry key leading more than one `##` entry heading in
          plan.md, are each a failure of this check on their own,
          whatever the other side holds. Report EVERY repeated key by
          name and by the side it repeats on — "`1.1` occurs twice in
          tasks.md", "`2.3` occurs twice in plan.md" — and BLOCK. Two
          entries keyed alike are duplicates whether or not their
          titles differ; the key is what must be unique.

          A stage-one BLOCK does NOT end the check. Stage one does not
          short-circuit: stage two is evaluated whatever stage one
          found, and each stage reports its own findings, so an input
          that carries BOTH a duplicate and a set difference yields
          both sets of findings in ONE run rather than revealing the
          second only after the first is repaired. Evaluating stage
          two on duplicated input is safe and costs nothing: reducing
          each collection to a set cannot invent a difference that was
          not already there.

          Stage one's message is DISTINCT from stage two's
          missing/extra-key message because the two are different
          defects with different repairs: a duplicate is repaired by
          renumbering one of the two, a missing or extra key by adding
          or removing one. A set comparison cannot see a duplicate at
          all — the set absorbs it — which is why this stage runs
          first and why the set comparison alone does not establish
          the 1:1 this check is named for.

          STAGE TWO — SET EQUALITY. Now reduce both collections to
          sets. Compare the two sets in BOTH directions and report
          each difference individually: a task number with no entry key,
          and an entry key matching no task number. Equal counts do
          not pass this check — tasks `{1,2,3}` against plan `{1,2,9}`
          fails in both directions. If plan.md exists but no entry key
          can be collected from it, the plan is not keyed 1:1 to the
          tasks and that is itself a failure of this check.

          ANY of the following → BLOCK, and every one that holds is
          reported, not just the first: a repeated key on either side
          (stage one), either difference non-empty, a task line
          carrying no task number, no collectable entry key, or no
          plan.md.

          The two stages together are the whole of the 1:1 claim in
          this check's name, and they claim nothing beyond it: unique
          on each side plus equal as sets is exactly a bijection
          between the two key collections. This check reads keys
          only — that an entry's contract text actually describes its
          task is review judgement, never this check.
```

# 你的工作

上面是一份驗證規則。下面是一組待驗的 `tasks.md` 與 `plan.md`。

**只依據上面那份規則**判斷這組輸入的結果，並且**只輸出下面兩行**、不要有任何其他文字：

```
VERDICT: <PASS 或 BLOCK 或 UNDETERMINED>
BASIS: <一句話說明依據>
```

- `PASS` = 依規則沒有任何一條被違反。
- `BLOCK` = 依規則至少有一條被違反。
- `UNDETERMINED` = 規則文字**無法**決定這個輸入該算哪一種。

⚠️ 不要使用任何工具、不要讀取任何檔案、不要搜尋任何程式庫。判斷所需的一切都在本檔內。
