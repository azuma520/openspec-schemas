# 盲測操作程序（凍結版）

> 與 `prompt.md` 同時交給盲測執行者。RED、GREEN 兩次執行使用同一份文字，唯一允許替換的是 kit 目錄根層的 `schema.yaml` 內容。

## 案例目錄怎麼對應到規則檔的檢查對象

- 把每個案例子目錄（`case-01`、`case-02`……）視為一個獨立的 repository root——規則檔裡提到「repository root」、「repository」時，指的就是這個子目錄本身，不是 kit 目錄，也不是這個子目錄以外的任何路徑。
- 每個案例子目錄底下有一個 `openspec/` 樹。規則檔裡提到「正在被檢查的 change」時，指的是 `openspec/changes/` 底下**除了 `archive/` 以外的那一個目錄**——每個案例只有一個這樣的目錄。
- `openspec` CLI（版本 1.3.1）已經在 PATH 上，可以直接在案例子目錄內執行。

## 寫入類指令的處理

- 規則檔裡有些指令會寫入或改變 repository 的狀態（例如任何形式的 `openspec archive`、或任何會修改檔案系統狀態的指令）。**這類指令不可以直接對案例子目錄本身執行**。
- 需要執行寫入類指令時，先把該案例子目錄整個複製一份到 kit 目錄以外的暫存位置（你自己建立、只給你自己用的複本），在複本上執行，再回頭把觀察到的結果套用到你對這個案例的判定。複本用完後留在原地即可，不需要清理。
- 讀取類指令（例如任何形式的 `validate`、`show`、一般檔案讀取）可以直接對案例子目錄執行，不需要複本。

## 天生不適用的檢查

- 規則檔裡有些檢查的輸入是「這個 repository 的 git 歷史」（例如讀 commit log、比對 branch）。案例子目錄不是一個有意義的 git 歷史（即使裡面存在 `.git`，也不能反映這個案例要測的狀態）。**任何一條檢查,只要它的判定依據是「這個 repository 的 git 歷史」，一律回報「不適用於 fixture」**，不要嘗試用案例子目錄裡任何 git 相關的觀察結果去猜一個判定。
- 除此之外的每一條檢查，都要嘗試在案例子目錄的實際內容上完整套用，不能因為「這條檢查看起來取決於 git」以外的其他理由跳過。

## 禁止讀取範圍

- 不要讀 kit 目錄以外的任何檔案，也不要讀你自己建立的複本以外的暫存檔案。這個限制只靠這份指示本身,你的檔案系統存取能力不會被技術手段擋下——所以這條規則的遵守完全依賴你自己照做,不代表違反了會被偵測到或阻止。

## GREEN 執行的產生程序（供派工者依循,執行者不需要讀這段的產生細節,只需要知道你手上這份就是照這個程序產生的）

GREEN 執行使用的案例子目錄集合,由派工者在對應的 change task 完成後,依下列程序重新產生一份(不沿用 RED 的任何複本或代號):

1. 取當時 working tree 的 `superpowers-bridge/schema.yaml` 全文,取代 kit 根層的 `schema.yaml`（檔名不變）。
2. 對每一個 fixture,重新指派一個中性代號(順序重新打亂,不沿用 RED 打亂時用過的順序或代號),複製其 `openspec/` 樹到新代號的子目錄。
3. 產生兩份實體上分開、但逐位元組相同(同一組代號、同一份 `schema.yaml`、同一份 `prompt.md`／`procedure.md`)的 kit 複本,分別交給兩位 GREEN 執行者(A、B 各一份),使其中一人不小心寫壞自己的複本不會影響另一人。
4. 產生的打亂代號 ↔ 原始 fixture 名稱對照表,存在 kit 目錄之外(不進 kit,不交給執行者)。

## 已知限制

執行者是具備檔案系統存取能力的 agent；「不要讀 kit 以外的檔案」這條規則只是指示,不是技術上的強制隔離——執行者的沙箱權限允許讀到 kit 以外的內容。這份器材的盲測性質建立在執行者遵守指示之上,不建立在存取隔離之上。
