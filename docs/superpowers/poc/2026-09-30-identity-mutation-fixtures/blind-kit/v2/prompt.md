# 盲測執行 prompt（凍結版 v2）

> 這份 prompt 逐字交給盲測執行者（一個對本 change 沒有脈絡的 agent）。RED、GREEN 兩次執行使用同一份文字，唯一允許替換的是下方「規則檔」的實際內容（檔名固定不變）。任何差異都要能用 `diff` 看出來。

---

你的任務是對一批獨立的 openspec 案例（case）逐一套用一份規則檔裡定義的檢查程序，並回報每個案例每一條檢查的判定。你**不知道**、也**不需要猜**任何案例「應該」得到什麼結果——你的工作就是照規則檔字面執行檢查、忠實回報。

## 你會拿到什麼

1. 一個案例目錄（kit 目錄），底下有多個子目錄，每個子目錄名稱是中性代號（例如 `case-01`、`case-02`……），內含一個獨立的 openspec repository（`openspec/` 樹）。把每個子目錄視為一個獨立的 repository root。
2. 一份規則檔，固定檔名 `schema.yaml`，放在 kit 目錄根層。規則檔內含若干條編號檢查（PRECHECK，以及編號 1、2、3……一路往上,直到規則檔內出現的最大編號為止——由你自己讀規則檔數出總共有幾條，不要假設任何固定數字）。
3. 一份操作程序文件（`procedure.md`，與本檔同目錄），說明每個案例要如何對應到規則檔的檢查對象、哪些步驟不適用、以及禁止事項。**先讀 `procedure.md`，再開始逐案例執行**。
4. 一個報告輸出路徑：`REPORT_FILE_PATH`（由派工者在執行時填入，是你唯一需要另外被告知的參數；kit 目錄本身是第二個參數）。

## 你要做什麼

對 kit 目錄底下**每一個**案例子目錄，重複以下步驟：

1. 依 `procedure.md` 的說明，找出這個案例目錄裡「正在被檢查的對象」。
2. 依規則檔逐條套用每一條檢查（PRECHECK 開始，然後編號檢查依序往上），對每一條產出一個判定。
3. 每一條檢查的判定，只能是下列五個固定 token 之一，**必須逐字寫成下面的英文大寫拼法（ASCII），不得翻譯、不得換成其他語言或腳本、不得自創同義詞**：
   - `PASS`（通過）
   - `BLOCK`（擋下）
   - `WARN`（警告，non-blocking）
   - `NOT_APPLICABLE`（`procedure.md` 指名這條檢查在案例目錄上天生無法成立時使用——與 v1 的「不適用於 fixture」同義）
   - `NO_VERDICT`（你嘗試套用這條檢查，但它沒有得出 PASS/BLOCK/WARN 的結論——**且這條檢查自己的規則文字沒有規定「得不出結論」要 BLOCK**。只要規則檔對這條檢查的文字明講「無法判定」或「得不出結論」的情況本身要擋下，就不能用 `NO_VERDICT`，必須用 `BLOCK`（並依第 4 步標注屬於哪一種）。`NO_VERDICT` 只用在規則文字對「得不出結論」這件事保持沉默、沒有另外規定擋下的情況。
4. 當某一條檢查的判定是 `BLOCK` 時，你還要在心裡（不需要在這條檢查旁另外寫一行）判斷這個 BLOCK 屬於下面哪一種、或兩種都屬於：
   - 這個 BLOCK 屬於「違規」：檢查本身可以完整執行，並且發現了一個真實的規則違反。
   - 這個 BLOCK 屬於「無法判定」：檢查無法完整、可靠地執行到底（不是因為規則規定它不適用，而是因為輸入讓判斷本身做不下去），因此以 BLOCK 呈報。
   - 同一條檢查、同一個案例，**兩者都可能同時成立**——如果是這樣，兩者都算進第 6 步的彙整。
5. 每一條檢查的判定旁邊附一行理由（一句話即可，不需要長篇論證；理由文字本身可以用任何語言書寫，只有判定 token 本身要求固定拼法）。
6. 完成該案例所有檢查後，寫一行最終結論，**必須是下面兩種形式中的其中一種，逐字比對，不得增減空格、不得加註解或佔位字**：

   ```
   FINAL: PASS
   ```

   或

   ```
   FINAL: BLOCK | categories=<list>
   ```

   `<list>` 是一個逗號分隔、**不含空格**的清單，內容是下面兩個固定 token 的子集合，每個最多出現一次、清單本身不可為空：`VIOLATION`（對應第 4 步的「違規」）、`UNDETERMINABLE`（對應第 4 步的「無法判定」）。例如 `categories=VIOLATION`、`categories=VIOLATION,UNDETERMINABLE`。這兩個 token 同樣必須逐字寫成英文大寫拼法，不得翻譯、不得換成其他語言或腳本、不得留白或寫 `(none)` 之類的佔位字。

   最終判定規則：只要這個案例裡**任何一條**檢查的判定是 `BLOCK`，這個案例就用 `FINAL: BLOCK | categories=<list>`；否則用 `FINAL: PASS`（`WARN`、`NOT_APPLICABLE`、`NO_VERDICT` 都不會單獨讓 FINAL 變成 BLOCK，`NO_VERDICT` 也永遠不會貢獻任何 category）。`<list>` 是這個案例**所有**檢查的**所有**BLOCK 判定，依第 4 步分類後取聯集（違規→`VIOLATION`、無法判定→`UNDETERMINABLE`），不重複列。

## 報告格式

把整份報告寫進 `REPORT_FILE_PATH` 這一個檔案（不要分散成多檔）。對每個案例，依下面的形狀輸出（案例之間用空行分隔即可，不需要額外的分隔符號）：

```
## <案例代號>

PRECHECK: <判定> — <一行理由>
1: <判定> — <一行理由>
2: <判定> — <一行理由>
...
<規則檔裡最大編號>: <判定> — <一行理由>

FINAL: PASS
```

或（若該案例任何一條檢查判定為 BLOCK）：

```
## <案例代號>

PRECHECK: <判定> — <一行理由>
1: <判定> — <一行理由>
...
<規則檔裡最大編號>: <判定> — <一行理由>

FINAL: BLOCK | categories=<list>
```

不需要總結整批案例的統計數字，也不需要對案例排名或比較——一個案例一份獨立的判定即可。

## 禁止事項

- 不要讀 kit 目錄以外的任何檔案（procedure.md 允許的「你自己建立的暫存複本」除外）。
- 不要執行任何會寫入案例目錄本身的指令；procedure.md 會說明需要用複本時怎麼做。
- 不要在報告裡加入你對「這個案例原本設計成什麼」的猜測或評論——只回報你依規則檔實際觀察與判定的結果。
- 不要假設檢查的總數、名稱或用途；一切以規則檔的實際文字為準。
